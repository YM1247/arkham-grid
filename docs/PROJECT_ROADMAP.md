# Arkham Grid 專案 Roadmap

## 文件目的

本文件描述 Arkham Grid 從目前的可完整通關 Run 原型，發展到可長時間遊玩、可維護與可發布版本所需的工作。它是後續開發的總體規劃來源；短期待辦請看 `Codex/TODO.md`，尚未決定的企劃與產品問題請看 `docs/OPEN_QUESTIONS.md`。

規劃遵守以下原則：

- 已由玩家確認的規則視為約束，不在後續階段自行推翻。
- 未決定的玩法、內容與產品方向以 Open Question ID 標記；問題回答前，不把任一選項當作既定方案。
- 優先建立能容納內容的穩定架構，再逐步增加內容量。
- 每個階段都必須保留可運行版本，並提供可重複的驗證方式。
- HP、Sanity、MP 與 AP 是核心壓力資源。普通戰鬥獎勵不得提供 HP／Sanity 回復或上限、AP 上限；MP 依節點固定回復。

## 目前完成性盤點（2026-09-09）

### 已可運作

- 8x8 棋盤、方塊拖放、放置驗證、Row／Col 消除與消除預覽。
- 友善初始盤面、跨戰鬥保留盤面、死盤扣除 10 Sanity 後重建盤面。
- 三張智慧手牌 v1、8 種普通方塊與 3 種特殊方塊。
- 玩家 AP、HP、護甲、Sanity、MP，以及力量、虛弱、堅硬、脆弱、再生、中毒。
- 多敵人戰鬥、目標鎖定、單體／擴散／全體／自身效果範圍。
- 八種資料化敵人意圖、獨立意圖索引、速度行動順序與最多五名敵人的穩定卡片 UI。
- 20 種統一咒文、6 種敵人、8 組遭遇、2 個事件、商店咒文商品與 20 項三選一獎勵。
- 可重現 10 層程序分層地圖、多起點分支、Boss 前休息、單一 Boss，以及新 Run、通關、兩種失敗與重新開始。
- 方塊形狀與咒文獨立抽取；每塊一個效果格、交叉消除只觸發一次，並由 MP 支付效果成本。
- 咒文獎勵直接加入咒文池；特殊形狀只解鎖一次，星點石板已降低抽取權重與智慧加成。
- 鎖定目標死亡後自動選取第一名存活敵人；敵人傷害下修並加入窺視、凝神防備等非傷害意圖。
- 條件式敵人意圖、4–7 回合戰鬥時限、逾時遞增 Sanity 壓力、菁英特殊形狀候選保底、消除支付預覽與咒文圖例。
- 版本化 JSON 內容註冊、跨檔案與內容關係驗證、JSON／`.tres` 正式責任分工。
- 可序列化 RunState、戰鬥輸入／輸出介面、還原前內容引用防護、固定 seed 棋盤／戰鬥／完整 Run 批次基線，以及 19 組自動測試。
- 一筆可玩的資料化多選項事件，包含代價／結果預覽、資源不足禁用、Sanity 來源記錄與事件內容範本。
- 兩段低 Sanity 與四種跨系統瘋狂效果，支援不重複疊加、回復解除、來源記錄與後果預覽。
- Python 內容驗證與 Godot 4.5.1 headless `res://main.tscn` 整合測試可重複通過。

### 尚屬原型或未接線

- 商店與休息已沿用事件選項 schema，具備可操作內容、資源預覽、不足禁用與節點結算；已有固定咒文商品，隨機庫存及特殊形狀商品尚未規劃。
- 事件 schema 與第一筆原創事件已接線；內部視聽資產方向已決定為 AI 輔助的簡約像素奇幻神話風格。
- 戰鬥 HUD、地圖與獎勵可完成功能驗證，但仍缺正式 Theme、視聽資產、設定／暫停畫面、焦點導覽與可及性。
- 已完成彼此獨立的單一 Run 自動槽、設定檔與共享 Meta 存檔；具備原子寫入、last-known-good 備份、損壞回退、嚴格解析及 RunState v1–v5 遷移。新職業與可取得的局外解鎖內容尚待製作。
- 尚未建立效能基線、分級記錄、匯出預設、資產授權清單與發布檢查表。

## 1. 架構與資料基礎

### 現況

Phase 11 已完成。`ContentRegistry`、`RunState`、戰鬥輸入／輸出、棋盤模型、敵人建立與 UI 均有清楚邊界；JSON 管理內容數值，`.tres` 管理行為原型。

### 目標

建立清楚的資料、Run、戰鬥、棋盤與畫面責任邊界，使內容擴充不必修改流程管理器，並讓純規則可以在無 UI 情況下測試。

### 前置條件

- 決定正式內容的單一資料來源與 `.tres` 的用途：`ARCH-001`。
- 存檔格式與行為已由 `SAVE-001` 至 `SAVE-004` 決定；磁碟服務與遷移器尚待實作。

### 執行內容

1. 建立資料註冊層，集中讀取 JSON、索引 ID、驗證引用並建立 runtime 資料物件。
2. 建立 `RunState` 類型，保存玩家 HP／Sanity／MP、AP、盤面效果格、手牌形狀／咒文、方塊池、咒文池、進度、獎勵與隨機狀態。
3. 將戰鬥開始輸入與戰鬥結果輸出改為明確資料介面，避免 Run 流程直接操作戰鬥內部節點。
4. 將敵人實例建立與敵人 UI 從戰鬥規則控制器分離；戰鬥規則只發送狀態與事件。
5. 將棋盤模型、手牌選擇演算法與 Control 視覺逐步拆開，保留現有拖放體驗。
6. 將 `main.tscn` 拆成至少可獨立載入的戰鬥、獎勵、地圖容器與結算畫面；在地圖未實作前可由流程控制器直接切換戰鬥與獎勵。
7. 為資料根節點加入 `schema_version`，並建立必要欄位、型別、值域、唯一 ID 與跨檔案引用規則。
8. 移除流程中的硬編碼 fallback 數值，或明確標記為載入失敗時的保底值並輸出可辨識錯誤。

### 交付成果

- 資料註冊層與版本化資料 schema。
- 可序列化的 Run 狀態模型。
- 明確的戰鬥輸入／輸出介面。
- 拆分後仍可單獨啟動的戰鬥場景。
- 架構圖與資料流說明。

### 驗收標準

- 資料可在不載入完整主場景時完成載入與驗證。
- 使用固定 RunState 可重建相同玩家配置、盤面與遭遇。
- 戰鬥結束只回傳結果，不直接決定下一個場景。
- 現有勝利、失敗、獎勵、跨戰鬥盤面與死盤行為維持不變。
- JSON 內容錯誤會在進入遊戲前被驗證工具或啟動檢查指出。

### 相關決策與依賴

`ARCH-001`、`BOARD-002`、`BOARD-005` 已決定並完成；`SAVE-001` 至 `SAVE-004` 已決定，實際磁碟存檔尚待實作。

## 2. 戰鬥系統收束

### 現況

Phase 12 已完成並配合核心改版更新。每名敵人擁有獨立意圖索引並依速度行動；八種意圖由資料驅動，死亡目標會自動換鎖。效果格、MP、狀態與結果都有測試入口。

### 目標

完成可預期、可檢查、可自動測試的戰鬥規則，使敵人組合、道具範圍與狀態時序真正成為策略來源。

### 前置條件

- 敵人意圖種類與資訊揭露：`COMBAT-001`。
- 多敵人行動及目標規則：`COMBAT-002` 至 `COMBAT-004`、`COMBAT-008`。
- 狀態與同時死亡規則：`COMBAT-005` 至 `COMBAT-007`。
- 道具分類方向：`CORE-001`。

### 執行內容

1. 為每名敵人保存自己的意圖索引、目前意圖與必要參數，不再使用單一共用 `enemy_intent`。
2. 依回答後的規格實作資料化意圖執行器；未知意圖必須驗證失敗，不能靜默退回普通攻擊。
3. 固定並測試玩家回合結束、玩家狀態、敵人逐一行動、敵人狀態、下一玩家回合的完整時序。
4. 將鎖定、擴散、全體與死亡後重新選擇規則集中到目標解析器。
5. 建立統一道具效果上下文，提供使用者、主要目標、目標集合、觸發 Row／Col、本回合觸發紀錄與 Run／戰鬥狀態。
6. 將連發手槍等條件效果從 `BattleManager` 特例移入資料化條件或效果實作。
7. 為每名敵人建立穩定 UI 節點，顯示 HP、護甲、狀態、意圖與鎖定狀態；數值更新只更新內容，不重建整組控制項。
8. 補齊勝利、HP 歸零、Sanity 歸零、中毒死亡、同一結算序列內敵我死亡等邊界測試。

### 交付成果

- 敵人獨立意圖狀態與資料化意圖執行器。
- 目標解析器與統一道具效果上下文。
- 可重用的敵人戰鬥 UI。
- 戰鬥規則測試案例。

### 驗收標準

- `intent_pattern` 中每個已允許值都有明確顯示與執行結果。
- 固定種子下，敵人意圖與行動順序可重現。
- 單體、擴散、全體與自身效果在敵人死亡前後都符合規格。
- 狀態的觸發、衰減與死亡時點沒有重複或漏算。
- 多敵人數值變動時不反覆建立目標按鈕。

### 相關決策

`CORE-001`、`COMBAT-001` 至 `COMBAT-008` 均已決定，完整規格見 `docs/COMBAT_SYSTEM.md`。

## 3. 局內成長與難度曲線

### 現況

Phase 13 已配合新核心遷移。Encounter 強度會產生 reward tier；咒文直接加入池，特殊形狀只解鎖一次。舊背包與 Row／Col 配置已退出正式 Run。

### 目標

完成 Phase 10 的玩家成長曲線，讓玩家透過構築效率追上遭遇壓力，同時保留 HP、Sanity 與 AP 的稀缺性。

### 前置條件

- 咒文升級與稀有度定義：`GROWTH-001`、`GROWTH-002`。
- 特殊方塊與成長上限：`GROWTH-003`、`GROWTH-004`。
- 獎勵 tier、槽位、重複與重抽規則：`REWARD-001` 至 `REWARD-005`。

### 執行內容

1. 將 `rarity`、`tier`、`balance_cost` 與升級關係帶入 runtime 資料。
2. 讓玩家在獎勵與戰鬥中查看咒文效果、MP 成本與池內構成。
3. 讓 encounter 產生可解釋的關卡強度值，作為敵人曲線與獎勵池輸入。
4. 建立有權重、稀有度、解鎖條件與去重規則的三選一候選器。
5. 讓特殊方塊與手牌規則成為可觀察的構築成長，而非單純無限制增加普通方塊。
6. 記錄每場戰鬥的回合數、消除 Row／Col 數、造成與承受傷害、護甲、Sanity 消耗、死盤次數及獎勵。
7. 使用 5–8 場固定測試路徑校正敵人總 HP、總攻擊與玩家預期成長。

### 交付成果

- 資料化獎勵候選器。
- 經確認的咒文／特殊形狀成長入口。
- 關卡強度與獎勵 tier 計算器。
- 戰鬥統計與平衡報告輸出。

### 驗收標準

- 同一關卡強度與隨機種子可產生可重現的獎勵候選。
- 第 4–8 場的成長不依賴普通 HP／Sanity／AP 獎勵。
- 普通戰鬥維持 2–4 回合目標，且中後期難度不因敵人數量突然失控。
- 每次數值調整可由統計結果與 `BALANCE_LOG.md` 追溯原因。

### 相關決策

成長與獎勵決策、`BOARD-001`、`BOARD-002`、`BOARD-004`、`BOARD-006` 已決定並完成；棄置或指定保留能力只由未來特殊道具／效果提供。

## 4. 完整 Run、地圖與節點

### 現況

Phase 14 已完成。Run 狀態機、固定 fallback 路線、程序分層 DAG、Boss、通關／失敗結算與重新開始已接線；事件、商店與休息均有資料化選項內容。

### 目標

建立從新遊戲到通關或失敗的完整單局流程，讓戰鬥、成長與資源壓力存在於清楚的路線與終點中。

### 前置條件

- Run 長度、Act／Boss、種子與結局：`RUN-001` 至 `RUN-004`。
- 節點種類與資源規則：`NODE-001`、`NODE-002`。
- 地圖與 RunState 的技術基礎由第 1 章提供。

### 執行內容

1. 定義 Run 狀態機：開始、地圖選擇、節點執行、戰鬥、獎勵、通關與失敗。
2. 建立版本化節點資料格式，描述節點 ID、類型、連線、內容引用、完成狀態與獎勵入口。
3. 依回答後的規格建立地圖生成或固定路線載入，確保起點到終點至少有一條合法路徑。
4. 讓盤面、HP、Sanity、MP、方塊池與咒文池依明確規則跨節點保存；戰鬥暫時狀態依規則重置。
5. 將戰鬥與獎勵從 `RunManager` 的直接函數鏈改為 Run 狀態機事件。
6. 加入新 Run、失敗後重新開始與通關結算流程。

### 交付成果

- Run 狀態機與地圖／路線資料。
- 經確認的節點場景與節點結果介面。
- 完整通關、失敗與重新開始畫面流程。

### 驗收標準

- 玩家可以從新遊戲一路完成或失敗一局，不需重啟主場景。
- 固定種子下，路線、遭遇與獎勵可重現。
- 六場之後不再無限循環 encounter。
- 每個節點只透過標準結果修改 RunState。

### 相關決策

`BOARD-003`、`RUN-001`、`RUN-002`、`RUN-003`、`RUN-004`、`NODE-001`、`NODE-002` 均已決定並完成第一版實作。

## 5. Sanity 與主題機制

### 現況

Sanity 上限 100、初始 70；所有變更已統一記錄來源。45／25 兩段門檻會加入不重複的跨系統瘋狂效果，回復後解除；魔法 tooltip 可預覽跨門檻與歸零後果。

### 目標

讓 Sanity 成為可預期但持續施壓的核心資源，並提供符合主題的低 Sanity 玩法，而不是只有第二條死亡計量表。

### 前置條件

- 門檻、效果、疊加、解除與資訊揭露：`SANITY-001` 至 `SANITY-005`。
- 敵人 Sanity 攻擊由第 2 章的意圖系統承接。

### 執行內容

1. 先建立資料容器，描述 Sanity 門檻、規則 ID、來源、持續條件與 UI 提示；問題回答前不填入實際瘋狂效果。
2. 將魔法成本、死盤懲罰、敵人壓力與節點事件統一走 Sanity 變更介面。
3. 為所有 Sanity 變化記錄來源，讓 UI、測試與平衡報告可區分成本與懲罰。
4. 依回答後的規格實作低 Sanity 規則與解除方式。
5. 模擬完整 Run 的 Sanity 消耗，確認玩家必須取捨，但不會因正常使用魔法而必然失敗。

### 交付成果

- Sanity 規則資料格式與統一變更介面。
- 低 Sanity UI 與經確認的瘋狂效果。
- Sanity 來源統計。

### 驗收標準

- Sanity 歸零仍直接結束 Run。
- 每次 Sanity 變動都能顯示並記錄來源。
- 普通戰鬥獎勵不稀釋 Sanity 壓力。
- 未回答的瘋狂效果不會被預先實作。

### 相關決策

`SANITY-001`、`SANITY-002`、`SANITY-003`、`SANITY-004`、`SANITY-005` 均已決定並完成第一版實作。

## 6. 內容管線與平衡工具

### 現況

Phase 16 已完成。Python 與 Godot 啟動驗證已覆蓋 schema、enum、值域、跨檔 ID、升級鏈、獎勵池、事件／商店／休息、地圖 DAG 與 RunState 引用；固定 seed 棋盤／戰鬥批次、九種已註冊內容範本及 schema 相容規範也已接入。

### 目標

讓新增內容有固定格式、能在啟動前發現錯誤，並以模擬和統計支援數值調整。

### 前置條件

- 各玩法 schema 隨對應章節確認後逐步加入。
